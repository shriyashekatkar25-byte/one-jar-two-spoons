the decision board

Does a shared Genie budget need a daily per-user cap?

Customer problem

A data team's admin funds one monthly Genie budget. Analysts use Genie Code in the workspace a few dollars a day. Now engineers can run Genie Code CLI agent loops from a terminal, and those count against the same jar.

One stuck loop can burn a week of an analyst's usage in an afternoon. If the jar empties on day 24, the people who did nothing wrong lose the last week.

Proposed change

When an admin creates a Genie budget that covers both surfaces, the setup flow pre-fills a daily per-user threshold (the new daily option) at a recommended dollar value, with a webhook alert when it trips.

The question this page answers: what value, and is it worth the friction for heavy CLI users on honest big days?

Success metric

P(shared budget runs dry before month end) ≤ 5% for teams that adopt the default, estimated from simulated months and then from real billing data.

Guardrails

Real CLI work days paused by the cap≤ 5%
Analyst workdays lost to an empty jar≤ 1%
Budget used (not over-throttled)≥ 75%
"Budget blocked me" support cases per 100 seatsno rise

Stakeholders

  • Account admins and FinOps owners (set the jar)
  • Analysts on Genie Code in the workspace
  • Data engineers on Genie Code CLI
  • Genie Code + AI Gateway eng, billing UX, support, field CS

pin it: the person who gets blocked is rarely the person who spent it.

the math, from my Monte Carlo course

Counting darts that land past the line

Probability = a fraction of random throws

"Will the jar run dry?" has no tidy formula once you mix 40 people, weekends, long tails and runaway loops. So I don't solve it. I replay the month many times with a seeded random number generator and count.

Each simulated month is a coin that comes up "dry" or "not dry". If I run n months and X run dry, then X is Binomial(n, p), and the share X/n is an unbiased estimate of p.

p̂ = X / n    SE = √( p̂(1−p̂) / n )

Variance shrinks like 1/n, so 4× the months halves the error bar. The running chart shows it settling.

Expectations are just averages

The guardrails are expected values: average analyst workdays lost, average share of real CLI days paused, average spend. Each is a sample mean over simulated months, and the Strong Law of Large Numbers says those sample means converge to the true expectations.

E[lost days] ≈ (1/n) Σ lostₖ

Product trick: the cap finder reuses the same seed for every cap. The only thing that changes between columns is the policy, so differences are the policy's effect, not noise.

how I'd run it on real data

From billing rows to a default

1 · daily spend per user and surface (SQL)

-- illustrative: lab.genie_spend_daily is a view built on
-- system.billing.usage (column names simplified)
CREATE OR REPLACE TABLE lab.user_day AS
SELECT account_id,
       user_id,
       usage_date,
       surface,                    -- 'GENIE_CODE_CLI' or workspace
       SUM(list_cost_usd) AS spend_usd
FROM   lab.genie_spend_daily
WHERE  usage_date >= date_sub(current_date(), 90)
GROUP  BY ALL;

-- how heavy is the CLI tail?
SELECT surface,
       percentile_approx(spend_usd, 0.50) AS p50,
       percentile_approx(spend_usd, 0.95) AS p95,
       percentile_approx(spend_usd, 0.99) AS p99
FROM   lab.user_day
GROUP  BY surface;

2 · replay months with resampled days (Python)

import numpy as np
days = spark.table("lab.user_day").toPandas()
rng  = np.random.default_rng(2026)

def p_dry(acct, budget, cap, n=4000):
    pool = days[days.account_id == acct].spend_usd.values
    users, d = 40, 30
    dry = 0
    for _ in range(n):
        s = rng.choice(pool, size=(d, users))  # resample real days
        if cap: s = np.minimum(s, cap)
        dry += s.sum() >= budget
    p = dry / n
    return p, 1.96 * np.sqrt(p * (1 - p) / n)

for cap in [0, 30, 40, 60]:
    print(cap, p_dry("acme", 8000, cap))
